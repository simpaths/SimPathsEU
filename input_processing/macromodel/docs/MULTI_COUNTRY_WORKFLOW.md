# Multi-Country DSGE Model Workflow

## Overview

This document describes the workflow for creating country-specific DSGE models for SimPaths integration. The German model serves as the template; other countries (Spain, Poland, UK, Sweden) follow the same structure with country-specific calibration and estimation.

## Model File Architecture

The DSGE model uses a **template + wrapper** pattern for multi-country support:

```
input_processing/macromodel/
  Macromodel_template.mod              ← Shared structural equations (DO NOT RUN DIRECTLY)
  Macromodel_Germany.mod               ← Thin wrapper: @#define country = "Germany" + @#include
  Macromodel_Poland.mod                ← Thin wrapper: @#define country = "Poland" + @#include
  Macromodel_Spain.mod                 ← Thin wrapper: @#define country = "Spain" + @#include
  Macromodel_Sweden.mod                ← Thin wrapper: @#define country = "Sweden" + @#include
  Macromodel_UK.mod                    ← Thin wrapper: @#define country = "UK" + @#include
  Macromodel_[COUNTRY]_frozen.mod      ← Auto-generated by generate_frozen_model.m
  country_params/
    Germany_calibration.mod            ← Parameter values, steady-state ratios
    Germany_estimation.mod             ← Shocks, priors, measurement errors, datafile
    Poland_calibration.mod
    Poland_estimation.mod
    Spain_calibration.mod
    Spain_estimation.mod
    Sweden_calibration.mod
    Sweden_estimation.mod
    UK_calibration.mod
    UK_estimation.mod
```

**Adding a new country** requires creating 3 files:
1. `country_params/{Country}_calibration.mod` — parameter values
2. `country_params/{Country}_estimation.mod` — shocks, priors, data config
3. `Macromodel_{Country}.mod` — 2-line wrapper

| File | Purpose |
|------|---------|
| `Macromodel_[COUNTRY].mod` | Wrapper → estimation (runs Dynare) |
| `Macromodel_[COUNTRY]_frozen.mod` | Simulation (auto-generated, posterior modes hardcoded) |

## Parameter Classification

### Tier 1: Universal (Fixed Across All Countries)

These are "deep" parameters with strong theoretical foundations:

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `beta` | 0.99 | Quarterly discount factor (~4% annual) |
| `sigma` | 2.0 | Inverse intertemporal elasticity of substitution (IES 0.5) |
| `alpha_m` | 0.5 | Matching function elasticity (Petrongolo & Pissarides 2001) |
| `eta` | 0.5 | Hosios efficiency condition |

### Tier 2: Country-Specific Calibration (From Data/Literature)

These vary by country but are calibrated, not estimated:

| Parameter | Description | Source | Notes |
|-----------|-------------|--------|-------|
| `chi_L` | Labor force share, L/WAP | Eurostat LFS | Age 15-64, estimation-sample mean |
| `chi_u` | Unemployment **share**, U/WAP | `chi_L` × sample-mean ILO rate | **Not** the U/L rate |
| `chi_n` | Total employment share, N/WAP | Derived: `chi_L - chi_u` | Total employment, the concept of the observable `n` |
| `delta` | Separation rate | OECD EPL data | Higher for flexible markets |
| `lambda_w` | Wage stickiness | Institutional | Collective bargaining coverage |
| `phi_pi`, `phi_y` | Taylor rule | Literature | ECB for €-zone, BoE for UK, Riksbank for Sweden |

> **Calibrate `chi_L` and `chi_u`; derive `chi_n`. Never the other way round.**
> The identity (eq. 10) requires `chi_u = chi_L - chi_n`, but `chi_L` and `chi_n`
> are two large, similar numbers, so computing `chi_u` as their difference
> amplifies any rounding by more than an order of magnitude. Rounding Poland's
> `chi_n` from 0.6777 to 0.70 would turn `chi_u` from 0.052 into 0.030, a 43% error
> in the coefficient scaling the whole latent u channel, which costs about 156 log
> points of marginal likelihood. Deriving `chi_n` from `chi_u` keeps errors proportional.
>
> **Use the estimation-sample mean unemployment rate, not a recent window.** The
> model is linearised around the sample it is estimated on. Poland 2005-2025
> averages 7.16% (range 2.7-18.3%); the 2018-2023 window alone gives 4.1%.
> `test_calibration_identities.m` checks both the identity and that the implied
> rate matches the sample.
>
> **`chi_u` is a share of the working-age population, not the U/L rate.** Entered
> as the U/L rate it is too big by a factor of about 1/`chi_L`.

**Country-specific values:**

| Parameter | Germany | Poland | Spain | Sweden | UK |
|-----------|---------|--------|-------|--------|-----|
| `chi_L` | 0.77 | 0.73 | 0.74 | 0.81 | 0.775 |
| sample-mean U/L rate | 5.44% | 7.16% | 15.37% | 7.27% | 5.44% |
| `chi_u` = `chi_L`×rate | 0.0419 | 0.0523 | 0.1137 | 0.0589 | 0.0422 |
| `chi_n` = `chi_L`−`chi_u` (derived) | 0.7281 | 0.6777 | 0.6263 | 0.7511 | 0.7328 |
| `delta` | 0.025 | 0.035 | 0.040 | 0.030 | 0.045 |
| `lambda_w` | 0.75 | 0.65 | 0.70 | 0.75 | 0.60 |

*All five rates are computed from the countries' own estimation samples
(`data_for_dynare_levels_{COUNTRY}.csv`, `u_level` column). The UK's `chi_L` is
the OECD LFS participation rate 15-64, 2000q1-2025q1 mean 77.53%: Eurostat, the
source of Sweden's, has no UK data after Brexit.*

### Tier 3: Estimated from Country Data

Only `omega_h`, `phi_inv_r` and the shock standard deviations are estimated; every
other structural parameter is fixed at its calibrated value because the identification
problems are structural rather than data-specific. The country estimation file is the
authority — the Poland priors below are illustrative of the shape, not a second copy to
maintain.

| Parameter | Prior (Poland) | Description |
|-----------|----------------|-------------|
| `omega_h` | Beta(0.35, 0.10) | Hours weight in production |
| `phi_inv_r` | Gamma(0.50, 0.25) | Cost-of-capital sensitivity of investment |
| `stderr eps_a` | InvGamma(0.50, 0.25) | Technology shock |
| `stderr eps_d` | InvGamma(0.50, 0.25) | Demand shock |
| `stderr eps_r` | InvGamma(0.40, 0.15) | Monetary shock |
| `stderr eps_p` | InvGamma(0.70, 0.30) | Cost-push shock |
| `stderr eps_L` | InvGamma(0.15, 0.06) | Labour force shock |
| `stderr eps_h` | InvGamma(0.35, 0.10) | Hours shock |
| `stderr eps_inv` | InvGamma(0.60, 0.25) | Investment shock |

## Data Requirements per Country

### Series (8 observables and the population, quarterly)

`varobs` in `Macromodel_template.mod` is the authority for the observables: `y inv c pi R n L h`.

| Variable | Description | Source |
|----------|-------------|--------|
| `y` | Real GDP | National accounts |
| `inv` | Gross fixed capital formation | National accounts |
| `c` | Household final consumption | National accounts |
| `pi` | Inflation (HICP, QoQ annualised) | Eurostat |
| `R` | Short-term interest rate | Central bank |
| `n` | Persons in employment, employees and self-employed, national concept | National accounts (`namq_10_pe` `EMP_NC`; Destatis `ERW060`; OECD QNA table 0110 for the UK) |
| `L` | Labour force, national concept | Labour force survey |
| `h` | Hours per person employed: total hours worked over persons in employment, both domestic concept | National accounts (`namq_10_a10_e` over `namq_10_pe`; Destatis `STD007`; OECD QNA table 0111 for the UK) |
| `pop_level` | Resident population, all ages, census breaks spliced: the planner's consumers, not a DSGE observable | Eurostat `demo_pjan` (1 January); Destatis `BEV020` for Germany; ONS `UKPOP.A` (mid-year) for the UK |

All eight observables are supplied as **Ramsey-detrended** 100×log-deviations by `ramsey_trend.m`,
not as HP-filtered cycles. `R` and `pi` are rate variables and enter as demeaned
percent. The HP-filtered file (`data_for_dynare_hp_{COUNTRY}.csv`) exists only as a
benchmark for `run_detrending_benchmark.m` and is not the estimation input.

### Sample Period

Set in `{Country}_estimation.mod` and bounded by `startdate`/`enddate` in
`make_datasets.do`. Germany starts 2000q1 (EMU), Poland 2005q1 (data availability
after EU accession), Spain 2000q1 (matching Germany; Spain is a 1999 euro founder,
but the OECD LFS stocks only begin 1999q1 and 2000q1 leaves them a year of
burn-in), Sweden 2001q1 (a pure data constraint — the OECD LFS stocks begin
2001q1, which happens to sit well inside the inflation-targeting regime adopted
in 1993, so the sample is one monetary regime), the UK 2000q1 (the OECD LFS
stocks begin 1999q2; the Bank of England has set rates independently since
1997, so the sample is one monetary regime too). COVID (2020q1-2021q2) is censored
to missing in the estimation file; Dynare's Kalman filter handles the gap.

### The UK: no Eurostat data

Eurostat stopped publishing UK data after Brexit: `namq_10_gdp` and `namq_10_pe`
end at 2020q3, the HICP at 2020m11 and `irt_st_m` at 2024m3. The UK block of
`make_datasets.do` takes each concept from the ONS or the OECD instead, for the
whole sample, with no splicing:

| Concept | Other countries | UK |
|---|---|---|
| Volumes (GDP, C, I, G, X, M) | Eurostat `CLV15_MEUR` | ONS chained volumes, re-referenced to 2015 and converted at the fixed 2015 rate |
| D1, D11 | Eurostat `namq_10_gdp` | ONS `DTWM`, `DTWL` (S.1 uses: the domestic concept) |
| Persons in employment, hours | Eurostat `namq_10_pe`, `namq_10_a10_e` | OECD QNA tables 0110/0111 (hours in millions, rescaled) |
| Resident population | Eurostat `demo_pjan`, 1 January (Germany: Destatis, quarterly) | ONS `UKPOP.A`, mid-year (30 June on q3) |
| Price level | Eurostat HICP, X-13ARIMA-SEATS from Stata (`hicp_q_sa.dta`) | ONS CPI `D7BT`, the UK's HICP, X-13ARIMA-SEATS from Stata with the same spec (`hicp_q_sa_uk.dta`) |
| 3-month rate | Euribor (ECB) or Eurostat `irt_st_m` | OECD STES, the same monthly-average concept |

Three checks in `make_datasets.do` hold these to the other countries' concepts
(contract 39 in `Integration_Contracts.md`): the ONS-based GDP must lie within 5%
of Eurostat's own UK `CLV15_MEUR` series where that exists (2026-10 vintage: -0.3%
to +3.3%, ONS revisions since 2020), the fixed rate is read off Eurostat's UK GDP
pair like Poland's and Sweden's, and hours per person employed must lie in [200, 700]
per quarter for every country. Where both exist, ONS `D7BT` equals Eurostat's UK HICP in
all 299 months of 1996m1-2020m11.

The re-referencing is not cosmetic. A chain-linked component is valued at its
reference year's relative prices, so the base-year shares `calibrate_growth_model`
reads (C/Y, I/Y, NX/Y) depend on the reference year, not only on a currency factor.
Re-referencing each ONS volume by its own 2015 current-price total puts it on
Eurostat's `CLV15` basis.

### The population workbook's growth reaches the estimation sample

`demographic_L_{country}.csv` follows the SimPaths workbook from the handoff quarter
(2023q1) on, and that quarter lies inside the estimation sample, so the workbook's
growth over 2023q1-2025q1 enters the estimated `L` observable as well as the forward
`N` path. This matters for the estimation alone: the DSGE takes no labour input from
SimPaths at runtime (contract 38), but a step in the workbook reads as a labour-force
shock in the sample's last quarters. The UK workbook's working-age population falls
1.2% from 2023 to 2024 (the note in `UK_growth_params.json`), while the observed labour
force rises, and the UK's `L` goes from -0.41 in 2023q1 to +3.10 in 2025q1, against a
sample standard deviation of 0.70. Poland's workbook steps the other way: `L_demo` grows
2.3% over 2023 while the labour force is flat, and its `L` goes from +1.55 in 2023q1 to
-1.10 in 2024q1.

`demographic_P_{country}.csv` follows the workbook's population of all ages from the same
quarter on, but the planner's in-sample consumers do not: like its in-sample workers they
are the HP trend of the data (`pop_level`, as `N` is of `n_level`), and after the last data
quarter both are chained on the workbook's growth. Poland's `P_demo` grows 2.5% over 2023,
the workbook's step between its 2023 and 2024 columns, while the resident population of the
data stage falls 0.4%; that step stays out of the in-sample population path and out of the
consumption trend `C = P c`. Because the stacked solve is global, the forward paths of `N`
and `P` still reach the in-sample trend: the planner of the first sample quarter already
knows the dependency ratio of 2060 and saves for it, which shapes the in-sample capital and
consumption trends and the estimated `c` observable. `run_full_workflow` re-solves step 0b
when step 0c changed either demographic file.

### Currency: euro volumes, national-currency wages

Two rules, for any country with its own currency:

- **Chain-linked volumes may be in euro.** Eurostat's `CLV15_MEUR` is
  `CLV15_MNAC` converted at the *fixed 2015* exchange rate, a constant rescaling
  (0.10691 for SEK) that drops out of every ratio and log deviation the Ramsey
  and DSGE layers use. All five countries' volumes are therefore in euro (the
  UK's rebuilt on the same basis from ONS data) and `K_0`, `Y_0` are comparable
  in level terms.
- **Current-price wage aggregates must be in the currency of the price index
  that deflates them.** Eurostat converts `CP_MEUR` at the *current* exchange
  rate. `real_wage_per_employee` divides by the domestic HICP, so a euro
  numerator puts every exchange-rate swing into the "real" wage. For Sweden the
  implied conversion factor runs from 0.085 to 0.119 over 2001-2025; for Poland
  the wage at current rates falls 28% between 2008q3 and 2009q1 while output per
  hour is flat. Poland's and Sweden's D1/D11 are therefore `CP_MNAC`, and the UK's
  are the ONS's GBP series.

The deflated national-currency wage is then converted to euro at the *fixed*
2015 rate, the same constant Eurostat applies to the volumes, so `w_level` is
euro at 2015 rates for every country, like the other level columns. The do-file
reads that rate off the GDP pair `CLV15_MEUR / CLV15_MNAC` (`gdpr / gdpr_nac`)
and stops if the ratio is not constant. A country with its own currency joins
`non_euro` in `make_datasets.do` and fetches `gdpr_nac` next to `gdpr`. The UK
does the same with Eurostat's UK GDP pair, which ends in 2020q3 but is constant
for as long as it runs (1.377714 EUR per GBP); it supplies the rate and a
cross-check, and the ONS-based volume then replaces `gdpr` (see "The UK: no
Eurostat data" above). `w_level` is diagnostic only: `w` is not in `varobs` and
no MATLAB stage reads the column.

### Interest rate

`R` is the monthly average of the last month of the quarter for every country:
ECB Euribor for Germany and Spain, Eurostat `irt_st_m` for Poland (WIBOR) and
Sweden, OECD STES `GBR.M.IR3TIB` for the UK, whose `irt_st_m` series stops at
2024m3 (over 1999m1-2024m3 the two differ by -0.002 pp on average and at most
0.12 pp). OECD MEI `POL.IR3TIB01.ST.M` is no substitute for Poland: it ends in
2024-01 and is an end-of-month value, so it must not be spliced onto the Eurostat
series.

### Data Preparation

Extend the Stata script `make_datasets.do` with a country branch. For each country:
1. Add a `series_codes_q` block with that country's dbnomics provider/dataset/series IDs
2. Map them onto the internal variable names the rename block expects
3. Set `startdate`/`enddate`
4. Add the HICP series to `make_datasets_hicp.do` (its Eurostat code and output name)
   if it is not already there; X-13 adjusts every series listed there.
   A country Eurostat does not cover needs its own price-level file, as the UK's
   `hicp_q_sa_uk.dta` from `make_datasets_hicp_uk.do`, selected through `hicp_file`
5. Add the SimPaths population workbook as `input/{CC}/align_popProjections.xlsx`.
   `build_population_projection` reads its `Population_projections` sheet, or,
   failing that, the sheet named after the country code (the SimPaths UK layout).
   It supplies the forward growth of `N` (ages 15-64) and of `P` (all ages)
6. Add the resident population series: a row in `series_codes_a` for annual figures
   (Eurostat `demo_pjan`, 1 January) or in `series_codes_q` for a quarterly series, and
   the locals `pop_freq`, `pop_var`, `pop_anchor_q` (the quarter an annual figure sits
   on), `pop_divisor` (to thousand persons) and `pop_break_periods`. List in
   `pop_break_periods` every period whose figure is the first on a new census basis,
   from the source's own break flags (Eurostat's flag `b` in `demo_pjan`); a series the
   source revises back after each census, or a register-based one, has none, and the
   series block says so. `splice_breaks.ado` replaces the growth into each listed
   period, `PROVENANCE_{Country}.txt` records each replacement, and
   `tests/test_data_loading.m` fails if a quarterly log step of `pop_level` reaches 0.01

## Workflow: Creating a New Country Model

### Step 1: Add the country to the data pipeline

Add the country branch to `stata/make_datasets.do` (see above) and run it from
`input_processing/macromodel/stata/`. It writes `input_processing/macromodel/data/data_for_dynare_levels_{COUNTRY}.csv`,
which is the input to the Ramsey layer.

### Step 2: Create the growth-model parameter file

```
country_params/{Country}_growth_params.json
```

Copy `Poland_growth_params.json` and set the structural inputs: `alpha_K`, `sigma`,
`delta_annual`, `beta_annual`, `base_year`, `tfp_growth_annual`, the
`terminal_growth` block, and the inflation target. Copy the `terminal_growth` block
unchanged: every country converges to the same long-run TFP growth at the same speed.
Set `tfp_growth_annual` by the rule in the templates' comments, and check where the
perpetual-inventory capital stock starts against the balanced-growth $K/Y$ (`K_override`).
`base_year` **must** equal the
year of the first row of the levels CSV — `ramsey_trend.m` asserts this.

### Step 3: Create the DSGE country files

```
country_params/{Country}_calibration.mod   # parameter values
country_params/{Country}_estimation.mod    # priors, shocks, datafile
Macromodel_{Country}.mod                   # 2-line wrapper
```

Calibrate `chi_L` and `chi_u` from that country's own sample and **derive** `chi_n`
(see the Tier 2 warning above). `test_calibration_identities.m` will fail loudly if
the triple is inconsistent or the implied rate does not match the estimation sample.

### Step 4: Run the full workflow

```matlab
>> run_full_workflow('Spain')
```

This executes, in order (the step labels are the ones the workflow prints):
- 0a. Ramsey growth-model calibration (`calibrate_growth_model`)
- 0b. Ramsey trend solve and detrending (`ramsey_trend`)
- 0c. SimPaths-aligned population projection (`build_population_projection`). Step 0b reads the
  demographic tail that 0c writes, so when 0c changes `demographic_L_{country}.csv` the workflow
  solves 0b a second time on the new demographics and reports how far the terminal anchor moved.
- 0d. Ramsey projection diagnostic plot
- 1. Bayesian estimation (Dynare)
- 2. Frozen-model generation (`generate_frozen_model`)
- 3. Dynamic policy-matrix export for SimPaths (`export_dynamic_for_simpaths`)
- 4. Postestimation analysis and summary report

Optional example (skip postestimation):

```matlab
>> run_full_workflow('Spain', 'skip_postestimation', true)
```

## Consistency Verification

After generating models for all countries, verify:

### 1. Parameter Plausibility

Check that the estimated structural parameters lie in reasonable ranges:
- `omega_h` ∈ [0.2, 0.5] (hours weight)
- `phi_inv_r` > 0 and well inside its prior's support (cost-of-capital channel)

### 2. Cross-Country Comparisons

Expected patterns:
- Higher `delta` (separation rate) for UK, Spain (flexible markets)
- Higher `lambda_w` (wage stickiness) for Germany, Sweden (collective bargaining)

### 3. Policy-Matrix Sign Verification

For all countries, verify the impact (t=0) responses in the exported bundle
(`irfs_eps_L.csv`, `irfs_eps_h.csv`):
- L↑ → w↓ (labour supply increase reduces wages)
- L↑ → π↓ (disinflation from the wage channel)
- h↑ → w↑ (hours increase **raises** the wage). `w` is the bargained wage per
  *worker*, and hours per person employed raise the per-worker marginal product the
  reset wage bargains over: in `Macromodel_template.mod`,
  ∂`w_star`/∂`h` = (1 − β·`lambda_w`)·`eta`·`alpha_n`·`omega_h` > 0 for any
  admissible calibration. A negative response here would indicate an export
  bug, not the expected pattern. The wage per hour, `w − h`, falls, and that
  is the cycle SimPaths applies (`SimPaths_Coupling.md` §3.2).
- h↑ → π↓ (marginal cost falls: the marginal product rises at once, the
  staggered wage only partly)

All four patterns hold in the committed Poland and UK bundles (checked 2026-11-09 on
period 0 of `irfs_eps_L.csv` and `irfs_eps_h.csv`).

Remember that the exported matrices hold **raw `ghu`** entries: a one-standard-deviation
response is `ghu(y, eps_j) * sigma_j` (multiply, never divide), for every shock, `eps_L` and
`eps_h` included: all are innovations in standard-deviation units, and the labour force and hours
follow their calibrated AR(1) (contract 37). See contracts 1, 3 and 37 in
`docs/Integration_Contracts.md`.

## Troubleshooting

### Common Issues

1. **Estimation fails to converge**
   - Check data for outliers (especially COVID period)
   - Try different mode_compute option (4, 6, or 9)
   - Verify priors are not too tight

2. **Blanchard-Kahn conditions violated**
   - Check Taylor rule satisfies Taylor principle (φ_π > 1)
   - Verify discount factor β < 1
   - Check for typos in parameter values

3. **Cross-country parameter differences seem implausible**
   - Review data sources for consistency
   - Check seasonal adjustment methods match
   - Verify sample periods are comparable
